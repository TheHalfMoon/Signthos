# Specification 001 — Pre-CI Execution Evidence Addendum

Status: CANDIDATE_NORMATIVE_ADDENDUM
Issue: #4
Canonical base: `f30cd1faa1246b2ff9123191da29d09c9b248d68`

## Problem

Specification 001 requires formatting, linting, tests, dependency resolution, and other executable evidence in Grains C–H before the permanent repository CI workflow is authorized in Grain I.

The currently available connected execution environments are unable to provide that evidence for Grain C:

- the ChatGPT execution container has no Rust toolchain and no usable network/package cache;
- CodeRabbit verified the exact Grain C head but its current runner is read-only and cannot install Rust or execute Cargo;
- adding the permanent `.github/workflows/provenance.yml` early would violate the dependency ordering that assigns canonical CI integration to Grain I.

The evidence requirement MUST NOT be waived or converted into a review-only PASS.

## Narrow authorization

Before Grain I, Specification 001 may use a **verification-only remote branch** solely to execute tests for an already-existing exact candidate commit.

This authorization does not add `.github/workflows/**` to any Grain C–H merge candidate path allowlist and does not move `S1-T078` or any Grain I task earlier.

A verification-only branch MUST satisfy all of the following:

1. its name begins with `verify/spec001-`;
2. it is created from the exact candidate SHA that is being tested;
3. the only content it may add beyond that candidate tree is `.github/workflows/spec001-ephemeral-verify.yml`;
4. that workflow is execution infrastructure only and MUST NOT be merged into the implementation PR or canonical `main` before Grain I;
5. the workflow MUST checkout the exact candidate SHA explicitly, not `HEAD`, a branch name, a moving ref, or a merge ref;
6. the workflow MUST print and assert the checked-out SHA before running qualification commands;
7. it MUST use no repository secrets, credentials, paid services, deployment environments, networked application services, or privileged write actions;
8. permissions MUST be read-only (`contents: read`) unless GitHub requires a narrower built-in permission to publish ordinary test logs; no write permission is authorized;
9. it may install the public Rust toolchain and resolve/download public Cargo packages solely to build/test the bounded provenance tool;
10. it MUST run only commands already required by the active grain or needed to prove its exact dependency graph/toolchain state;
11. workflow success is execution evidence only. It does not substitute for independent substantive semantic review, live review-evidence verification, exact-head qualification, rights evidence, or expected-head merge protection;
12. the implementation candidate SHA MUST remain unchanged while its workflow evidence is being used for qualification;
13. if implementation changes after the run, the old workflow evidence is stale and MUST NOT qualify the new head;
14. after evidence is captured, the verification branch MUST receive a cleanup commit removing the ephemeral workflow before it is considered dormant; the branch itself MUST never be merged;
15. if branch deletion is unavailable through the connected tooling, leaving a cleaned verification branch ref is permitted only when its tip contains no `.github/workflows/**` delta relative to the tested candidate and its non-merge status is recorded in the implementation PR evidence.

## Workflow contract

The ephemeral workflow MUST be minimal and deterministic. For Rust grains it may perform, as applicable:

- checkout of the exact candidate SHA;
- installation of the exact required Rust toolchain/components;
- `cargo generate-lockfile` only when the active grain is explicitly resolving a candidate lockfile in a disposable checkout;
- `cargo metadata` and `cargo tree` for dependency evidence;
- `cargo fmt --check`;
- `cargo clippy --all-targets -- -D warnings`;
- focused/full `cargo test`;
- grain-owned validator or NOTICE commands when already authorized by that grain.

A generated lockfile from an ephemeral run is evidence, not repository content. Any lockfile committed to an implementation branch must be independently reconciled against the printed/generated bytes and then re-tested with `--locked` on the exact new candidate head.

## Evidence binding

A qualifying execution record must identify at minimum:

- tested candidate SHA;
- verification branch and workflow commit SHA;
- workflow run id;
- runner operating system/image when reported by GitHub;
- exact Rust/Cargo versions when relevant;
- exact command exit statuses;
- test counts;
- dependency graph/lock evidence when relevant;
- whether any command was skipped or unavailable.

GitHub workflow success alone is insufficient if logs do not prove the workflow checked out the declared candidate SHA.

## Boundary with Grain I

Grain I still exclusively owns the first **canonical persistent** workflow at `.github/workflows/provenance.yml` and repository CI integration under `S1-T078`–`S1-T084`.

This addendum authorizes only non-merge, temporary execution infrastructure needed to satisfy evidence-dependent gates that precede Grain I. It does not authorize changing branch protection, required checks, repository rulesets, release automation, deployments, publishing, source import, or product runtime.

## Source and rights boundary

This addendum does not authorize:

- Documenso or Stirling product/application source;
- restricted/commercial source access;
- credentials or private package registries;
- paid external services;
- relicensing;
- legal/compliance claims;
- Specification 002.

Synthetic fixtures and the public Rust/crates.io toolchain needed for Specification 001 remain the only execution inputs authorized by this addendum.

## Effectiveness gate

This addendum is ineffective until:

1. its exact candidate head receives independent substantive review against the canonical Constitution, `AGENTS.md`, Spec 001 `spec.md`, `plan.md`, and `tasks.md`;
2. any findings are reconciled and the exact head is re-evaluated;
3. qualification records absent/skipped checks accurately;
4. merge uses `expected_head_sha` protection; and
5. canonical `main` is post-merge verified to contain only this addendum.

Only after that post-merge verification may a `verify/spec001-*` branch be created under this authority.
